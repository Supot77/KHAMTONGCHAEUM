# เบื้องหลังระบบแยกคำและตรวจคำซ้ำ

ตรวจจากโค้ดและฐานข้อมูลจริงวันที่ 21 ตุลาคม 2026 ระบบหลักอยู่ใน `lib/rooms.ts`, `lib/game.ts`, `lib/gemini.ts`, `lib/word-analysis.ts` และ `lib/sql-store.ts`

## 1. ใครทำหน้าที่อะไร

| ส่วน | หน้าที่ |
|---|---|
| โมเดล | เลือกคำตั้งต้น แบ่งพยางค์และจัดประเภทคำที่ยังไม่มีข้อมูล และตัดสินความเชื่อมโยงเฉพาะเมื่อโหวตเสมอหรือไม่มีเสียง |
| โค้ดเซิร์ฟเวอร์ | ตรวจตาและสิทธิ์ผู้เล่น อ่านฐานคำ ตัดสินผ่าน/ไม่ผ่านจากประเภท เทียบรูปเขียนพยางค์ จัดการผู้แพ้ คะแนน และข้อมูลย้อนหลัง |
| ผู้เล่น | ตัดสินความเชื่อมโยงผ่านชาเลนจ์/โหวต และช่วยแก้พยางค์หรือประเภทคำตอนสรุป |
| ฐานข้อมูล | เก็บสถานะห้องแยกจากความรู้เกี่ยวกับคำ เพื่อให้คำเดิมใช้ข้อมูลซ้ำข้ามห้องได้ |

ฐานคำกับประวัติคำที่เล่นเป็นคนละอย่าง การพบคำในฐานคำหมายความว่ามีข้อมูลภาษาให้ใช้ ไม่ได้แปลว่าคำนั้นผิดกติกาหรือเคยถูกใช้ในรอบนี้

## 2. ผู้เล่นกดส่งแล้วเกิดอะไรขึ้น

หน้าเว็บส่งคำพร้อมรหัสห้อง เซสชัน รหัสคำสั่ง และหมายเลขตาไป `/api/room` เซิร์ฟเวอร์ตรวจว่าผู้เล่นมีสิทธิ์เล่นในตานั้น ห้องยังไม่หมดอายุ และไม่ได้อยู่ในช่วงดีเบต

คำผ่านการปรับ Unicode เป็น NFC ตัดช่องว่างหัวท้าย และตรวจความยาว 1–200 หน่วยอักขระตาม JavaScript รวมถึงชุดตัวอักษรและเครื่องหมายที่อนุญาต ขั้นนี้ยังไม่ได้ตรวจคำนามหรือแยกพยางค์

จากนั้นบันทึกคำเป็น `pending` พร้อมรหัสเฉพาะของคำ ผู้ส่ง และรหัสคำก่อนหน้า แล้วเปลี่ยนตากับเริ่มเวลาของผู้เล่นถัดไปทันที ผู้เล่นจึงไม่ต้องรอ Gemini แม้คำเดิมจะมีในฐานแล้ว การอ่านฐานคำและตรวจจริงยังอยู่ในขั้นตอนตรวจแยกต่างหาก

ระหว่างเล่น API ส่งเฉพาะคำล่าสุดให้หน้าเว็บ ประวัติเต็มอยู่ที่เซิร์ฟเวอร์ จะแสดงเมื่อจบช่วงคำเพื่อให้ตรวจทาน

## 3. งานตรวจเริ่มจากฐานข้อมูล

หน้าเว็บอ่านสถานะประมาณทุก 1 วินาที เมื่อมีงานค้างจะเรียก `/api/check` เซิร์ฟเวอร์จองสิทธิ์ทำงานของห้องไว้ 65 วินาที เพื่อไม่ให้ทุกแท็บเรียกโมเดลพร้อมกันสำหรับห้องเดียวกัน

หนึ่งงานเลือกคำที่ยังไม่มีผลวิเคราะห์ได้ไม่เกิน 6 รายการ ตัดข้อความที่เหมือนกันในชุดออกก่อน แล้วอ่าน `word_analysis_cache` ด้วยกุญแจสามส่วน:

```text
รุ่นกติกา + ชื่อโมเดล + ข้อความคำที่ปรับ NFC/ตัดหัวท้ายแล้ว
```

รุ่นกติกาปัจจุบันคือ `thai-noun-titles-v1` ถ้าพบข้อมูลจะใช้ทันที ถ้ายังไม่พบจึงส่งเฉพาะคำที่ขาดให้โมเดลวิเคราะห์รวมเป็นชุด การเปลี่ยนชื่อโมเดลหรือรุ่นกติกาทำให้ต้องหาข้อมูลในกุญแจชุดใหม่ อาจมีการวิเคราะห์คำเดิมอีกครั้ง

ช่องว่างภายในคำหรือชื่อผลงานยังเป็นส่วนหนึ่งของกุญแจ จึงไม่ได้รวมทุกข้อความที่อ่านเหมือนกันให้เป็นแถวเดียวกันอัตโนมัติ

## 4. ข้อมูลที่โมเดลต้องส่งกลับ

ตัวอย่างผลสำหรับ ปลาดาว เป็นเพียงรูปแบบข้อมูลที่คาดหวัง:

```json
{
  "syllables": ["ปลา", "ดาว"],
  "category": "noun",
  "nounType": "common",
  "reason": "คำนามเรียกสัตว์ทะเล",
  "suggestions": [],
  "titleContext": ""
}
```

`category` แยกเป็น noun, verb, adjective, adverb, sentence, phrase, other หรือ uncertain ส่วน `nounType` แยกคำนามทั่วไป ชื่อเฉพาะ อาการนาม ชื่อเพลง ภาพยนตร์ และซีรีส์

โมเดลได้รับเฉพาะรายการคำสำหรับงานวิเคราะห์ภาษา ไม่ได้รับทั้งสายคำเพื่อให้ตัดสินว่าซ้ำหรือเชื่อมกันหรือไม่ และถูกกำชับให้ถือข้อความผู้เล่นเป็นข้อมูล ไม่ทำตามคำสั่งที่แฝงอยู่ในคำนั้น

เซิร์ฟเวอร์ตรวจ JSON และความสอดคล้องของประเภท เช่น ถ้าไม่ใช่ noun ต้องไม่ระบุว่าเป็นชื่อเพลง ชื่อผลงานต้องมีข้อมูลระบุตัวผลงานใน `titleContext` ผลที่ผ่านถูกเก็บเป็น `source=model` ซึ่งเป็นฉบับร่างที่ใช้ซ้ำได้ รวมทั้งคำที่ถูกจัดว่าไม่ใช่คำนามและคำที่ไม่แน่ใจ

## 5. แบ่งตามการอ่าน แต่เทียบรูปเขียน

ระบบขอให้โมเดลแบ่งพยางค์โดยคงตัวสะกด สระ วรรณยุกต์ และตัวการันต์ เช่น ทะเล → ทะ / เล และ จันทร์ → จันทร์ ห้ามแปลง จันทร์ เป็น จัน เพียงเพราะอ่านคล้ายกัน

โค้ดตรวจว่าชิ้นส่วนไม่ว่าง มีรูปแบบที่ยอมรับ และเมื่อนำมาต่อกันต้องได้ตัวอักษร เครื่องหมายประกอบ และตัวเลขเดิมครบตามลำดับ โดยไม่นับช่องว่างหรือเครื่องหมายคั่น ไม่ยอมให้โมเดลเติมตัวอักษรที่ไม่ได้เขียน เช่น เติม ะ ให้พยัญชนะที่มีเสียงสระแฝง

การตรวจนี้ยืนยันความครบของรูปเขียน แต่ยังพิสูจน์ไม่ได้ว่าขอบเขตทุกพยางค์อ่านถูกจริง โปรแกรมยังไม่มีพจนานุกรมการอ่านหรือเครื่องแยกพยางค์อิสระที่ตรวจคำตอบ Gemini ซ้ำได้ทั้งหมด

## 6. โค้ดตรวจซ้ำอย่างไร

เมื่อมีพยางค์ของคำก่อนหน้าและคำปัจจุบัน โค้ดหาแต่ละพยางค์ที่เขียนเหมือนกันทุกตัว ถ้ามีอย่างน้อยหนึ่งพยางค์ถือว่าซ้ำ ไม่ต้องเรียกโมเดลมาตัดสินคู่คำอีก

| คำก่อนหน้า | คำใหม่ | ผลตรวจพยางค์ |
|---|---|---|
| ปลา | ปลาดาว | ซ้ำ ปลา |
| ทะเล | ทะเลสาบ | ซ้ำ ทะ และ เล |
| จันทร์ | จันทน์ | ไม่ซ้ำ เพราะรูปเขียนต่างกัน |
| ปลา → แมว | ปลา | ถ้าอยู่ในช่วงคำเดียวกัน จะเทียบ ปลา ล่าสุดกับ แมว เท่านั้น จึงไม่ถูกตัดสินซ้ำจาก ปลา ที่อยู่ห่างออกไป |

ตัวอย่างที่ไม่ซ้ำยังต้องผ่านกติกาคำนามและการพิจารณาความเชื่อมโยงด้วย ระบบไม่ได้ห้ามใช้คำจากประวัติทั้งวง และไม่ได้หาพยางค์ซ้ำภายในคำเดียวกันเพื่อปรับแพ้

## 7. คำนาม การ/ความ สี และชื่อผลงาน

โค้ดใช้ประเภทจากฐานคำหรือโมเดล: noun ให้ตรวจพยางค์ต่อ ประเภทที่ชัดว่าไม่ใช่ noun ให้แพ้ ส่วน uncertain ให้ผู้เล่นทบทวน และไม่เรียกโมเดลวนซ้ำสำหรับคำที่มีผล uncertain แล้ว

คำสั่งวิเคราะห์กำหนดตัวอย่าง วิ่ง → การวิ่ง, สุข → ความสุข, แดง → สีแดง ตามกติกาเรื่องสี โดยไม่บังคับเติมคำนำหน้าให้ทุกคำ การบ้าน เป็นคำนามอยู่แล้ว ส้ม มีความหมายเป็นผลไม้ และ ฟ้า มีความหมายเป็นท้องฟ้า จึงไม่ถูกปฏิเสธเพราะเป็นชื่อสีได้ด้วย

โมเดลต้องพิจารณาข้อความทั้งชิ้น ประโยคที่มีคำนามอยู่บางคำไม่ได้ผ่านโดยอัตโนมัติ แต่ชื่อเพลง ภาพยนตร์ หรือซีรีส์ที่รู้จักจริงผ่านในฐานะชื่อเฉพาะได้ แม้ชื่อจะเป็นประโยคยาว ถ้าไม่มั่นใจว่าเป็นชื่อจริงให้ uncertain

กฎภาษาเหล่านี้อยู่ในคำสั่งโมเดล โค้ดไม่ได้มีพจนานุกรมครบทุกคำมาโต้แย้งประเภทที่โมเดลตอบ จึงยังพลาดได้ โดยเฉพาะคำหลายความหมาย ชื่อใหม่ และชื่อที่โมเดลจำผิด `titleContext` เป็นคำอธิบายจากโมเดล ไม่ใช่หลักฐานจากการค้นเว็บ ระบบยังไม่มีฐานรายชื่อผลงานหรือการค้นเว็บอัตโนมัติมายืนยัน

## 8. ถ้าตรวจพบความผิดทีหลัง

เช่นผู้เล่นส่ง ปลา → ปลาดาว → ท้องฟ้า → เมฆ ต่อกันระหว่างรอ เมื่อพบ ปลาดาว ซ้ำกับ ปลา ระบบระบุผู้ส่งและพยางค์ที่ซ้ำ ตัด ปลาดาว กับคำต่อท้ายออกจากสายคำ แล้วให้ผู้ส่ง ปลาดาว ตกรอบจากเซ็ต คนต่อท้ายไม่ถูกตัดสินว่าแพ้ตาม

เมื่อจบช่วงนี้จะเปิดสรุปคำและรายการคำต่อท้ายที่นำไปใช้ใหม่ได้ คนที่ยังอยู่ในเซ็ตเริ่มสายคำใหม่ด้วยคำตั้งต้นใหม่ ถ้าเซ็ตเหลือผู้เล่นคนเดียวก็สรุปผู้ชนะเซ็ต

ถ้ามีการประกาศคนแพ้จากเหตุอื่นไปก่อนแล้ว เช่นหมดเวลาหรือแพ้ชาเลนจ์ ผลวิเคราะห์ที่มาทีหลังจะใช้ประกอบหน้าทบทวน ไม่ย้อนเปลี่ยนคนแพ้และแต้มที่ตัดสินแล้ว

ปัจจุบันไม่มีแต้มต่อจำนวนคำ แต้มมาจากสามคนสุดท้าย ผู้ชนะเซ็ต และผู้ชนะชาเลนจ์

## 9. ผู้เล่นช่วยแก้ข้อมูลอย่างไร

เมื่อจบช่วงคำ ทุกคนเสนอการแบ่งพยางค์และประเภทคำได้ ข้อเสนอยังอยู่ในข้อมูลห้องและยังไม่เขียนทับฐานคำกลาง เจ้าของห้องต้องกด ยืนยันและบันทึกฐานคำ จึงบันทึกเป็น `source=players`

คำแก้ต้องคงตัวสะกดเดิมและรูปแบบข้อมูลต้องผ่านการตรวจเช่นเดียวกับผลโมเดล ถ้ายังเลือก uncertain จะยืนยันเป็นฐานคำไม่ได้ ผลจากผู้เล่นที่ยืนยันแล้วจะไม่ถูกฉบับร่างจากโมเดลเขียนทับ ใช้กับการตรวจครั้งถัดไปในกุญแจรุ่นกติกา/โมเดลเดียวกัน ไม่ย้อนตัดสินรอบที่จบแล้ว

การกด รับรองคำ ระหว่างเล่นเป็นการรับรองเฉพาะคำครั้งนั้น ต่างจากการยืนยันฐานคำหลังจบช่วง

## 10. การประหยัดโทเคนและการทำงานพร้อมกัน

คำเดิมที่พบในฐานใช้โทเคนวิเคราะห์คำเป็นศูนย์ เก็บทั้งผลผ่านและไม่ผ่านเพื่อไม่เสียโควตาตรวจคำกริยาเดิมซ้ำ ส่วนการเลือกคำตั้งต้นและการตัดสินโหวตเสมอยังเป็นการเรียกโมเดลแยกต่างหาก

หลังงานตรวจสำเร็จจะเว้นช่วงตรวจประมาณ 4 วินาที ข้อผิดพลาดจะหน่วงลองใหม่ตามชนิด โดยโควตา 429 รอประมาณ 60 วินาที คำยังรอตรวจ ไม่ถูกถือว่าเป็นคำผิดเพียงเพราะ API ล้มเหลว ไม่มีการเปลี่ยนไปโมเดลเสียเงินอัตโนมัติ

การจองงาน 65 วินาทีเป็นระดับห้อง ยังไม่มีตัวจองคำกลางทุกห้อง ถ้าสองห้องพบคำใหม่เดียวกันพร้อมกันจริง ๆ อาจเรียกโมเดลซ้ำได้ก่อนที่อีกห้องจะบันทึกผล แต่เมื่อมีแถวแล้วการใช้งานครั้งต่อไปจะอ่านฐาน

การเขียนสถานะห้องใช้หมายเลข revision และ compare-and-swap ส่วนคำแต่ละครั้งมีรหัสเฉพาะกับรหัสช่วงเกม จึงไม่เอาผลเก่ามาใช้กับคำที่ส่งใหม่หรือช่วงใหม่เพียงเพราะข้อความตรงกัน

งานวิเคราะห์เริ่มจากหน้าเว็บเรียก `/api/check` ปัจจุบันยังไม่มี worker ที่ไล่ตรวจทุกห้องต่อเนื่องเมื่อปิดเว็บหมดทุกแท็บ ต่างจากงานล้างห้องที่เป็นงานตั้งเวลาบน Neon และทำงานได้โดยไม่มีคนเปิดเว็บ

## 11. ลบห้องเมื่อไม่มีคนใช้งานครบ 1 ชั่วโมง

เก็บ `last_active_at` ในตาราง rooms เมื่อผู้เล่นทำคำสั่งสำเร็จหรือหน้าเว็บที่มองเห็นส่ง heartbeat ประมาณทุก 60 วินาทีจะต่ออายุห้อง การอ่านสถานะปกติและผลจากงานโมเดลไม่ต่ออายุ

เมื่อครบ 3,600,000 มิลลิวินาทีหลังใช้งานครั้งสุดท้าย เซิร์ฟเวอร์ไม่ให้กลับเข้าห้อง แม้แถวนั้นยังรอการลบจริง จะตอบ HTTP 410 และหน้าเว็บล้างเซสชันกลับหน้าตั้งวง

Neon Function `roomcleanup` ตรวจลบทุก 15 นาที ดังนั้นเวลาลบข้อมูลจริงอาจช้ากว่าเวลาหมดอายุได้ประมาณหนึ่งรอบงาน ลบเฉพาะข้อมูลใน rooms รวมสถานะเกมและแต้มของห้องนั้น ฐานคำกลาง word_analysis_cache ไม่ถูกลบ ข้อเสนอที่ยังไม่ยืนยันซึ่งอยู่เฉพาะในห้องจะหายไปพร้อมห้อง

## 12. หลักฐานปัจจุบัน

วันที่ 21 ตุลาคม 2026 ทดสอบอัตโนมัติ 43 กรณีผ่าน และ production build ผ่าน ทดสอบห้องหมดอายุกับ Neon จริงพบ HTTP 410 ห้องหมดอายุไม่คืนชีพจาก heartbeat ห้องที่ยังใช้ไม่ถูกลบ และฐานคำกลางยังอยู่

ทดสอบอ่านคำตัวอย่างเดิม 12 กรณีจาก Neon รายงาน `modelCalls=0` ส่วน log ของ Function ยืนยันว่าเคยลบห้องจริง เช่นรอบ `2026-10-20T15:00:00Z` ลบ 2 ห้อง และยังมีการเรียกงานต่อเนื่องตามเวลา

การยืนยันนี้ครอบคลุมโค้ดในเครื่องที่เชื่อม Neon และงาน Neon จริง ยังไม่ได้ยืนยัน URL production ที่ผู้ใช้ deploy บน Vercel
